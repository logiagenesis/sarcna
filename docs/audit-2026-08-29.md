# Comprehensive audit — 29 August 2026

A full review of the SARCNA 2027 codebase: the whole existing test suite run
from a clean install, then a line-by-line read of the code the suite does not
reach — authorisation, ownership, fulfilment arithmetic and output escaping.

**The suite was green before this audit started, and green is where it began.**
183 audit checks, 37 smoke checks and 8 race checks, all passing, twice, with
matching totals. Six defects were found behind that green tick. Every one is
fixed, and every one now has a check that was **first made to fail against the
old code** and then watched go green.

| | Before | After |
|---|---|---|
| `tools/audit.php` | 183 checks | **200 checks** |
| `tools/smoke-test.php` | 37 checks | **43 checks** |
| `tools/race-test.php` | 8 checks | 8 checks |

## What was checked

| Area | Method | Result |
|---|---|---|
| Whole suite, clean install | `ci-install` → smoke → race → audit ×2, on a fresh database | Green; totals identical across runs |
| Every PHP file parses | `php -l` over `app`, `public_html`, `tools` | Clean |
| SQL injection | Every interpolated SQL fragment traced to its source | **Clean** — every `{$clause}` is built from constants; all values are bound |
| Output escaping (XSS) | Every `<?= … ?>` in all 137 views, mechanically unwrapped past `e()`, `money()`, `picture()` and integer casts | **Clean** — no unescaped dynamic value reaches a page |
| Price tampering | Every path that writes `unit_price_cents` | **Clean** — prices always come from the database, never the request |
| Concurrency | Seat reservation and stock decrement | **Clean** — both are single conditional `UPDATE`s; the bed rule is a unique index |
| Password handling, reset and verification tokens | Read end to end | **Clean** — hashed tokens, single use, no email enumeration |
| Uploads | `PhotoService`, `AdminController::storeImage` | **Clean** — type read from the file's own bytes, re-encoded through GD (which is what strips EXIF), random names, `.htaccess` denies PHP under `/uploads` |
| Authorisation | Every route's capability, exercised as a real limited admin | **Four defects** — below |
| Order ownership | Every route that reads or changes an order by reference | **One defect** — below |
| Fulfilment arithmetic | Donations, stock, transport, coupons | **One defect** — below |

## The six defects

Each was reproduced against the running site before it was fixed, and the
reproduction is quoted.

### 1. Anyone could cancel anyone's pending order — no login, no CSRF

`GET /payment/cancelled?reference=…` called `OrderService::markCancelled()` on
any pending order whose reference it was given. It checked nothing else.

```
order PRB-KVB7-UDZP: before=pending_payment  after a stranger's GET (HTTP 200)=cancelled
```

An order reference is not a password. It travels in the confirmation email, in
the address bar and through PayFast. Worse, this is a **GET**, so it needs no
form and no token: an `<img src="https://…/payment/cancelled?reference=…">` on
any other page fires it from the victim's own browser. The effect is not just a
cancelled order — `markCancelled()` releases the shuttle seats the delegate was
in the middle of paying for.

**Fixed.** Cancelling now requires proof the order is yours: the session whose
cart became it, or the account that owns it. The page itself still renders for
anyone, so the honest return-from-PayFast path is untouched.

### 2. Any exporting admin could download every financial and personal record

The export route asked only for the broad `exports` capability, which four of
the seven roles hold. Signed in as a **transport admin**:

```
/admin/finance (the screen)   HTTP 403  blocked as intended
/admin/export/finance-pack    HTTP 200  DOWNLOADED (33 data rows)
/admin/export/customers       HTTP 200  DOWNLOADED
/admin/export/payments        HTTP 200  DOWNLOADED
/admin/export/messages        HTTP 200  DOWNLOADED
/admin/export/applications    HTTP 200  DOWNLOADED
/admin/export/refunds         HTTP 200  DOWNLOADED
```

The screen was correctly refused and the CSV of the same data was handed over.
That made the role separation the site advertises effectively decorative: a
volunteer given the shuttle job could take the convention's entire financial
position and the full delegate list.

**Fixed.** Each dataset now names the capability that governs its own screen,
and an unlisted dataset is refused outright, so adding an export without
deciding who may run it fails closed.

### 3. Service applications and contact messages were readable by every admin role

Both were gated on `admin:dashboard` — the one capability *every* role holds,
including `checkin_volunteer`, which `docs/admin-user-guide.md` describes as
"the check-in desk only".

```
/admin/applications    HTTP 200  READABLE
/admin/messages        HTTP 200  READABLE
```

Service applications carry clean time, phone numbers, home group and email
address. In a fellowship context that is the most sensitive data the site
holds — this is a project that ships a photo-anonymity notice.

**Fixed.** Both now answer to capabilities of their own, held only by a super
admin. That is what the documented role table always described; the code had
drifted from it.

### 4. Only the first donation in an order was ever recorded

`confirmDonations()` asked whether the **order** already had a donation before
writing each line. The first insert made the answer yes, so every donation
after it was skipped.

```
order has 2 donation line items, totalling R300.00
donations recorded after payment: 1
  - 7th Tradition Donation R100.00
recorded R100.00 of the R300.00 the delegate paid
```

This is reachable from the donations page as it ships, which sells more than
one donation type. The money was taken and *did* count as income — that total
is computed from `order_items` — but the donations ledger, the donations
screen, the donations CSV and the public "raised so far" figure all lost it.
The delegate's contribution simply never appeared.

**Fixed.** The check is now per line item, and `donations.order_item_id`
carries a unique index, so a repeated PayFast notification still cannot write a
donation twice. Migration:
`database/migrations/2026-08-29-add-order-item-id-to-donations.sql`.

### 5. The cart ignored the stock ceiling the product page enforces

`ShopController::add()` refuses more than the stock on hand and more than
`max_per_order`. `CartService::updateQuantity()` applied neither.

```
SARCNA 2027 Tote Bag: stock set to 3, max_per_order=5
asked the cart for 40 -> cart line quantity is 40
```

Forty of something with three in stock reached checkout and could be paid for.
Fulfilment then refused to take stock negative and logged a warning, which is
the right instinct — but by then the money had been taken for goods that do not
exist, and the committee's only clue was a line in the log.

**Fixed.** Changing a quantity in the cart applies the same two ceilings as
adding it.

### 6. A refund could be recorded against an order that was never paid

The order screen only offers the refund form on a paid order, but the form was
the only guard; the POST itself accepted any order. `FinanceService::summary()`
subtracts refunds from net income regardless of the order's status, so a refund
against an unpaid order would reduce the reported surplus by its full amount
while the order's total had never been counted as income.

**Fixed.** The controller now refuses any order that is not paid or already
refunded.

## Noted, not changed

Judgement calls, recorded so the next person does not have to rediscover them.

* **Merchandise oversell is quiet.** When stock runs short on a paid order,
  fulfilment logs a warning and writes an `inventory_movements` row reading
  "needs attention". Accommodation, by contrast, sets `admin_note` on the order
  and emails the committee. The asymmetry is real; with defect 5 fixed the
  remaining way to reach it is a genuine race between two buyers, which is
  rare and self-correcting at the stock level. Worth making symmetrical if
  merchandise volume grows.
* **The PayFast source-IP check fails open when DNS is unavailable**, and says
  so in the payment log. That is deliberate and documented in the code: the
  signature, amount and server-to-server confirmation checks all still apply,
  and failing a real payment over a DNS blip would be worse.
* **No Content-Security-Policy header.** The site uses inline `style`
  attributes throughout, so a useful policy would need `unsafe-inline` for
  styles and would be weaker than it looks. Given that output escaping came
  through this audit clean, this is a hardening item, not a fix — and it should
  be added deliberately, with the inline styles moved out first.
* **A password change does not invalidate other sessions.** Low impact on a
  site where sessions are short-lived and there is one device per delegate, but
  it is the conventional behaviour and is worth adding.
* **`markPaid()` guards against a duplicate notification by reading the order's
  status first.** Two genuinely simultaneous notifications could both pass that
  read. The individual fulfilment steps are each guarded on their own
  (donations and transport by existence checks, beds by the unique index,
  stock by a conditional update), so the outcome is safe; the guard is just not
  the thing making it safe.

## How to re-run this

```bash
php tools/ci-install.php http://127.0.0.1:8000   # fresh install through the real form
php tools/smoke-test.php                          # 43 invariant checks
php tools/race-test.php  http://127.0.0.1:8000    # 8 concurrency checks
php tools/audit.php      http://127.0.0.1:8000 --password=…   # 200 checks
```

Run the audit twice and check the totals match. The transcript of the run this
document reports is committed at [`docs/audit-result.txt`](audit-result.txt).

**If you change a check, break the thing it guards on purpose first and watch
it go red.** Every check added by this audit was verified that way; two of them
passed for the wrong reason on the first attempt and were caught only by doing
it.
